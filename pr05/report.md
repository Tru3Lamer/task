В рамках изучения шифрования был создан секретный файл pr05/files/secrets.txt, содержащий три строки с конфиденциальными данными: DB_PASSWORD=super_secret_password_123, API_KEY=sk-abc123def456 и ADMIN_TOKEN=eyJhbGciOiJIUzI1NiJ9.test. Этот файл был зашифрован с использованием публичного ключа владельца командой gpg --encrypt --armor --recipient magerisdeemperor@yandex.ru pr05/files/secrets.txt, в результате чего появился зашифрованный файл secrets.txt.asc. При просмотре зашифрованного файла видно, что исходные данные невозможно прочитать, так как они представлены в виде шифртекста — бессмысленного набора символов. Расшифровка файла была выполнена командой gpg --decrypt pr05/files/secrets.txt.asc с вводом пароля от приватного ключа. При вводе неверного пароля GPG выдаёт ошибку "gpg: decryption failed: Bad passphrase", и расшифровка не происходит. Также было установлено, что файл, зашифрованный для другого пользователя, невозможно расшифровать, поскольку он зашифрован публичным ключом получателя, а расшифровать его может только владелец соответствующего приватного ключа.

Для изучения цифровой подписи был создан файл pr05/files/agreement.txt с содержимым "Я, Павел Мишарин, подтверждаю что прочитал политику ИБ компании." и датой подписания. Для этого файла была создана отдельная подпись командой gpg --armor --detach-sign pr05/files/agreement.txt, в результате чего появился файл подписи agreement.txt.asc. Проверка подписи командой gpg --verify pr05/files/agreement.txt.asc pr05/files/agreement.txt показала результат "Good signature", что подтверждает целостность файла и его авторство. Команда gpg --verify проверяет, что файл не был изменён после подписания (целостность), что подпись принадлежит указанному владельцу ключа (подлинность) и что подпись создана именно этим ключом (аутентификация). После добавления в файл дополнительной строки "Дополнение: разрешаю списать мою зарплату" повторная проверка подписи показала результат "BAD signature", что означает, что файл был изменён и его хеш не совпадает с тем, который был подписан. Это доказывает, что цифровая подпись эффективно защищает файл от несанкционированных изменений.

В ходе изучения удаления файлов был проведён эксперимент, демонстрирующий разницу между командами rm и shred. При выполнении rm /tmp/secret-data.txt удаляется только запись в inode (метаданные файловой системы), а сами блоки с данными остаются нетронутыми до момента их перезаписи другими данными. Это было подтверждено поиском данных на диске командой sudo grep -a "TOP SECRET" /dev/sda1 2>/dev/null, которая показала, что данные всё ещё присутствуют на диске после удаления. Таким образом, данные после rm можно восстановить с помощью специальных утилит, пока блоки не перезаписаны. В отличие от rm, команда shred перезаписывает содержимое блоков случайными данными (по умолчанию 3 прохода) и нулями в финальном проходе, после чего удаляет файл. Выполнение команды shred -v -n 3 -z -u /tmp/to-be-shredded.txt показало три прохода перезаписи: pass 1/3 (random), pass 2/3 (random), pass 3/3 (random) и финальный проход pass 4/4 (000000), после чего файл был удалён. Поиск данных после shred с помощью grep не нашёл данных, что подтверждает невозможность восстановления информации после применения shred. Принципиальная разница между rm и shred заключается в том, что rm удаляет только запись в файловой системе, оставляя данные на диске, а shred физически перезаписывает блоки диска, делая данные невосстанавливаемыми.

Затирание свободного места необходимо в следующих сценариях: перед продажей или передачей диска другому лицу, чтобы предыдущий владелец не мог восстановить конфиденциальные данные; при утилизации компьютера или сервера для уничтожения остаточной информации; в организациях с высокими требованиями к информационной безопасности для соблюдения политики уничтожения данных; после удаления критически важных файлов для гарантии, что данные не будут восстановлены злоумышленниками. Демонстрация затирания свободного места была выполнена командой dd if=/dev/urandom of=/tmp/fill-free-space.tmp bs=1M count=100 2>/dev/null.

На контрольные вопросы были даны следующие ответы. Разница между шифрованием и подписью заключается в том, что шифрование преобразует данные в нечитаемый вид (шифртекст) с использованием ключа для обеспечения конфиденциальности, а подпись создаётся с использованием приватного ключа для обеспечения целостности и подтверждения авторства. Одновременно зашифровать и подписать файл можно с помощью флагов --sign --encrypt или --symmetric --sign. Публичный ключ можно раздавать всем, потому что он используется только для шифрования и проверки подписи, а расшифровать данные и создать подпись можно только с приватным ключом. Приватный ключ нельзя передавать никому, так как его компрометация позволит злоумышленнику расшифровывать все зашифрованные для владельца данные и создавать подписи от его имени. Если потерять приватный ключ, зашифрованные данные невозможно будет расшифровать, и они станут недоступными навсегда. Подделать Verified коммит на GitHub без приватного GPG-ключа владельца невозможно, так как GitHub проверяет подпись с использованием публичного ключа, добавленного в аккаунт, а без приватного ключа создание действительной подписи криптографически невозможно.

Shred плохо работает на SSD из-за технологии wear leveling (выравнивание износа) и TRIM, которые могут записывать данные в другие физические блоки, сохранять копии данных в оригинальных блоках и удалять данные до выполнения shred. Вместо shred для SSD рекомендуется использовать шифрование всего диска (LUKS), аппаратное Secure Erase или физическое уничтожение накопителя. Коллега, утверждающий, что форматирование диска перед продажей делает данные безопасными, не прав, потому что быстрое форматирование удаляет только таблицу разделов и метаданные файловой системы, оставляя данные физически на диске, которые могут быть восстановлены с помощью специализированных утилит. Безопасными способами являются полное форматирование с перезаписью нулями, использование shred или wipe, шифрование диска перед использованием и физическое уничтожение.

Отличие detach-sign от встроенной подписи заключается в том, что --detach-sign создаёт отдельный файл подписи (.asc), оставляя исходный файл без изменений, что удобно для распространения подписи отдельно от данных, а --sign встраивает подпись в файл, создавая бинарный файл с подписью внутри.
